# PayPal API engineering notes: escrow on sandbox (researched 2026-10-05)

Scope: a Next.js / TypeScript app where the **client** pays through PayPal Checkout into the **platform's sandbox business account**. The platform later **pays the freelancer with Payouts** or **partially refunds the client**.

> Repo note: `package.json` currently pins **next 16.3.8 / react 19.2.8**, not Next 15. Everything below works with the App Router on either version. It already depends on `@paypal/paypal-server-sdk@^2.5.0` and `@paypal/react-paypal-js@^10.5.2`.

How each fact was checked:
- **[spec]**: read from PayPal's official OpenAPI specs in `github.com/paypal/paypal-rest-api-specifications` (last commit 2026-04-07). Spec versions: Orders 2.32, Payments 2.12, Payouts 1.9, Webhooks 1.11, Disputes 1.11, Partner Referrals 2.5.
- **[npm]**: checked with `npm view` and by installing the package and reading its `.d.ts` files.
- **[docs]**: read on developer.paypal.com. Note that `docs.paypal.ai` now 301-redirects to `developer.paypal.com/docsai/...`.
- **[inferred]**: experience or best practice, not verified this session.

## 0. Decisions at a glance

| Topic | Decision |
|---|---|
| Server calls | Use plain `fetch` against REST in one `lib/paypal.ts` module. Use `@paypal/paypal-server-sdk` only where it helps (Orders and Payments are typed there). It has **no Payouts, Webhooks, Identity, Disputes or Referenced Payouts**, so you need fetch anyway. |
| Token | `POST /v1/oauth2/token` with client_credentials. Cache it in memory until `expires_in - 5 min` (it lasts about 9 h). Deduplicate concurrent refreshes. |
| Checkout | Orders v2, `intent: CAPTURE`. Set `payment_source.paypal.experience_context` (do **not** use the deprecated `application_context`). Put the escrow id in `purchase_units[0].custom_id` so it comes back in captures and webhooks. Send a `PayPal-Request-Id` on create and capture, and `Prefer: return=representation`. |
| Frontend | **JS SDK v6** through `@paypal/react-paypal-js/sdk-v6` (`PayPalProvider` + `PayPalOneTimePaymentButton`). It works with a plain `clientId`, so no client-token route is needed. The v5 `PayPalScriptProvider`/`PayPalButtons` is still exported from the package root as a fallback, but PayPal labels v5 "deprecated". |
| Release | `POST /v1/payments/payouts` with `recipient_type: EMAIL` and the receiver set to a **sandbox personal account email**. Note that Payouts amounts use **`currency`**, not `currency_code`. Make `sender_batch_id` deterministic (for example `release-<escrowId>`) so it cannot pay twice within 30 days. |
| Refund | `POST /v2/payments/captures/{id}/refund` with `amount` (partial) or `{}` (full), plus a `PayPal-Request-Id` (kept 45 days). |
| Webhooks | Create the webhook through the API or the dashboard and store `webhook_id`. Verify with **self-verification (CRC32 + RSA-SHA256)** or the postback API, using the **raw body**. Simulator events **cannot** be verified by postback, and their webhook id is the literal `WEBHOOK_ID`. |
| Login | Log in with PayPal (OIDC) at `https://www.sandbox.paypal.com/signin/authorize`. Exchange the code at `/v1/oauth2/token` with `grant_type=authorization_code`, then call `GET /v1/identity/oauth2/userinfo?schema=paypalv1.1` to get `payer_id`, `emails[]` and `verified_account`. |
| AI | `@paypal/agent-toolkit@1.11.0` has **no Payouts tools**, and its `ai-sdk` export targets **AI SDK v4** (`ai@^4`, `LanguageModelV1`). The current `ai` package is 7.x, so it is incompatible. If you want PayPal tools in an agent, use the remote MCP server (`https://mcp.sandbox.paypal.com/http`) or the toolkit's MCP server class with `@modelcontextprotocol/sdk`. It is useful for invoices, disputes and tracking, and not needed for the escrow core. |
| Production | Holding a client's money on your own PayPal balance and paying it out later is "escrow services". The PayPal AUP requires **pre-approval** for that, and it is money-transmitter territory. The production path is **PayPal Complete Payments / Multiparty**: onboard freelancers with Partner Referrals (`DELAY_FUNDS_DISBURSEMENT` feature), create orders with `payee.merchant_id` and `payment_instruction.disbursement_mode: "DELAYED"`, and release with `POST /v1/payments/referenced-payouts-items`. Funds auto-release after 28 days. |

## 1. OAuth2 client-credentials token

- `POST {API}/v1/oauth2/token`
- Headers: `Authorization: Basic base64(client_id:secret)` and `Content-Type: application/x-www-form-urlencoded`
- Body: `grant_type=client_credentials`
- Response:

```json
{ "scope": "https://uri.paypal.com/services/payments/... openid ...",
  "access_token": "A21AA...", "token_type": "Bearer",
  "app_id": "APP-80W284485P519543T", "expires_in": 32400, "nonce": "2026-10-05T...Z..." }
```

- `expires_in` is usually about 32,400 s (9 h). Live tokens are about 8–9 h; PayPal's own README says sandbox is "3-8 hours". **Cache the token and reuse it.** Do not mint one per request. **[inferred]** Hammering the token endpoint can be throttled (429).
- After you change app features in the dashboard (for example enabling Payouts or Log in with PayPal), the **scopes inside an already-cached token do not change**. Mint a new token.
- Browser-safe client token (only needed for some v6 features such as Fastlane or saved payment methods): use the same endpoint and add `response_type=client_token` (plus `domains[]=example.com` for Fastlane). It is valid for about 15 min (`expires_in: 900`). **Not needed for our flow; we use `clientId`.**

```ts
// src/lib/paypal/client.ts  (server-only)
import "server-only";

export const PAYPAL_API =
  process.env.PAYPAL_ENV === "live" ? "https://api-m.paypal.com" : "https://api-m.sandbox.paypal.com";

type Cached = { token: string; expiresAt: number };
let cached: Cached | null = null;
let inflight: Promise<string> | null = null;

export async function getAccessToken(): Promise<string> {
  if (cached && Date.now() < cached.expiresAt) return cached.token;
  if (inflight) return inflight;
  inflight = (async () => {
    const basic = Buffer.from(`${process.env.PAYPAL_CLIENT_ID}:${process.env.PAYPAL_CLIENT_SECRET}`).toString("base64");
    const res = await fetch(`${PAYPAL_API}/v1/oauth2/token`, {
      method: "POST",
      headers: { Authorization: `Basic ${basic}`, "Content-Type": "application/x-www-form-urlencoded" },
      body: "grant_type=client_credentials",
      cache: "no-store",
    });
    if (!res.ok) throw new Error(`PayPal token ${res.status}: ${await res.text()}`);
    const j = (await res.json()) as { access_token: string; expires_in: number };
    cached = { token: j.access_token, expiresAt: Date.now() + (j.expires_in - 300) * 1000 };
    return j.access_token;
  })().finally(() => { inflight = null; });
  return inflight;
}

export class PayPalError extends Error {
  constructor(public status: number, public body: any, public debugId?: string) {
    super(`PayPal ${status} ${body?.name ?? ""} ${body?.details?.[0]?.issue ?? body?.message ?? ""} (debug_id=${debugId})`);
  }
  get issue(): string | undefined { return this.body?.details?.[0]?.issue; }
}

/** Generic JSON caller. Pass requestId for every money-moving POST. */
export async function pp<T = any>(
  path: string,
  init: { method?: string; body?: unknown; requestId?: string; prefer?: "return=representation" | "return=minimal";
          mock?: string /* sandbox negative testing code */; headers?: Record<string, string> } = {},
): Promise<T> {
  const token = await getAccessToken();
  const headers: Record<string, string> = { Authorization: `Bearer ${token}`, "Content-Type": "application/json", ...init.headers };
  if (init.requestId) headers["PayPal-Request-Id"] = init.requestId;
  if (init.prefer) headers["Prefer"] = init.prefer;
  if (init.mock) headers["PayPal-Mock-Response"] = JSON.stringify({ mock_application_codes: init.mock });
  const res = await fetch(`${PAYPAL_API}${path}`, {
    method: init.method ?? (init.body !== undefined ? "POST" : "GET"),
    headers, body: init.body !== undefined ? JSON.stringify(init.body) : undefined, cache: "no-store",
  });
  const text = await res.text();
  const json = text ? JSON.parse(text) : undefined;
  if (!res.ok) throw new PayPalError(res.status, json, res.headers.get("paypal-debug-id") ?? json?.debug_id);
  return json as T;
}
```

Errors have this shape:

```json
{ "name": "UNPROCESSABLE_ENTITY",
  "details": [ { "issue": "INSTRUMENT_DECLINED", "description": "..." } ],
  "message": "...", "debug_id": "...", "links": [] }
```

Always log `debug_id`. PayPal support asks for it.

## 2. Orders v2: create and capture

### Endpoints [spec]
| Op | Endpoint | Useful headers |
|---|---|---|
| Create | `POST /v2/checkout/orders` | `PayPal-Request-Id`, `Prefer`, `PayPal-Partner-Attribution-Id`, `PayPal-Auth-Assertion`, `PayPal-Client-Metadata-Id` |
| Get | `GET /v2/checkout/orders/{id}` | |
| Patch | `PATCH /v2/checkout/orders/{id}` | |
| Capture | `POST /v2/checkout/orders/{id}/capture` | `PayPal-Request-Id`, `Prefer` |
| Authorize | `POST /v2/checkout/orders/{id}/authorize` | |
| Track | `POST /v2/checkout/orders/{id}/track` | |

- `PayPal-Request-Id` on Orders: "**The server stores keys for 6 hours**" (account manager can raise it to 72 h). A retry with the same id returns the original result instead of creating a second order or capture.
- `Prefer: return=minimal` returns only `id`, `status` and `links`. **`return=representation`** returns the full resource. Use it on capture so you get the capture id and fees in one call.
- Order `status` values: `CREATED | SAVED | APPROVED | VOIDED | COMPLETED | PAYER_ACTION_REQUIRED`.
- Payer redirect window: the caller has **6 hours** by default from creation to send the payer to the `approve` link.

### Create request (snake_case REST)
```jsonc
POST /v2/checkout/orders
PayPal-Request-Id: create-<escrowId>-<attempt>
Prefer: return=representation
{
  "intent": "CAPTURE",
  "purchase_units": [{
    "reference_id": "escrow_8f2c",            // <=256; your PU id (needed if >1 PU and you PATCH)
    "custom_id": "escrow_8f2c",               // <=255; NOT shown to payer; echoed on capture + webhooks  <- map webhooks with this
    "invoice_id": "KEPT-escrow_8f2c-1",       // <=127; shown to payer; MUST be unique per merchant account (DUPLICATE_INVOICE_ID)
    "description": "Milestone 1: landing page", // stored up to 127 chars (accepts 3000, truncates)
    "soft_descriptor": "KEPT ESCROW",         // 22 chars effective
    "amount": {
      "currency_code": "USD",
      "value": "110.00",
      "breakdown": {
        "item_total": { "currency_code": "USD", "value": "100.00" },
        "handling":   { "currency_code": "USD", "value": "10.00" }   // e.g. platform fee shown as handling, or make it an item
      }
    },
    "items": [{
      "name": "Milestone 1: landing page",    // shown truncated to 127
      "quantity": "1",                        // STRING, whole number
      "unit_amount": { "currency_code": "USD", "value": "100.00" },
      "category": "DIGITAL_GOODS",            // DIGITAL_GOODS | PHYSICAL_GOODS | DONATION
      "sku": "escrow_8f2c-m1"
    }]
  }],
  "payment_source": {
    "paypal": {
      "experience_context": {
        "brand_name": "Kept",                 // <=127
        "user_action": "PAY_NOW",             // PAY_NOW | CONTINUE
        "shipping_preference": "NO_SHIPPING", // GET_FROM_FILE | NO_SHIPPING | SET_PROVIDED_ADDRESS
        "landing_page": "NO_PREFERENCE",      // LOGIN | GUEST_CHECKOUT | NO_PREFERENCE | BILLING
        "payment_method_preference": "IMMEDIATE_PAYMENT_REQUIRED", // blocks eCheck (avoids PENDING captures)
        "locale": "en-US",
        "return_url": "https://app.example.com/escrow/escrow_8f2c/paypal/return",
        "cancel_url": "https://app.example.com/escrow/escrow_8f2c/paypal/cancel"
      }
    }
  }
}
```

Rules that cause 422 errors:
- `amount.value` must equal `item_total + tax_total + shipping + handling + insurance - shipping_discount - discount`. Otherwise you get `AMOUNT_MISMATCH`.
- `item_total` must equal the sum of `unit_amount * quantity` (`ITEM_TOTAL_MISMATCH`). If `items` is present, `breakdown.item_total` is required (`ITEM_TOTAL_REQUIRED`).
- Values are **strings** with currency precision ("100.00"; JPY has no decimals, otherwise `DECIMAL_PRECISION`).
- `application_context` still exists but is legacy. `payment_source.paypal.experience_context` replaces it.
- With JS SDK popup or modal flows, PayPal ignores `return_url`/`cancel_url`, but **they are used for redirect presentation mode** (v6 `presentationMode: "redirect"` or `"auto"` falling back on mobile). Always set them.

Response (representation, abridged): `{ id: "5O190127TN364715T", status: "PAYER_ACTION_REQUIRED" | "CREATED", links: [{rel:"payer-action"|"approve", href:"https://www.sandbox.paypal.com/checkoutnow?token=..."}, ...] }`. When `payment_source.paypal` is sent, the link rel is `payer-action`.

### Capture
```http
POST /v2/checkout/orders/{orderId}/capture
PayPal-Request-Id: capture-<orderId>
Prefer: return=representation
Content-Type: application/json

(empty body or {})
```
Read these fields (snake_case):

```ts
const pu = order.purchase_units[0];
const cap = pu.payments.captures[0];
cap.id                                   // CAPTURE ID -> store; needed for refunds
cap.status                               // COMPLETED | PENDING | DECLINED | PARTIALLY_REFUNDED | REFUNDED | FAILED
cap.status_details?.reason               // if PENDING: ECHECK, PENDING_REVIEW, UNILATERAL, RECEIVING_PREFERENCE_MANDATES_MANUAL_ACTION, ...
cap.amount                               // {currency_code, value}
cap.custom_id, cap.invoice_id            // echoed
cap.seller_receivable_breakdown          // { gross_amount, paypal_fee, net_amount, receivable_amount?, exchange_rate?, platform_fees? }
cap.seller_protection?.status
cap.final_capture
order.status                             // "COMPLETED"
order.payer.payer_id, order.payer.email_address
order.payment_source.paypal.account_id, .email_address, .account_status  // VERIFIED | UNVERIFIED
```

- **Only treat funds as held when `cap.status === "COMPLETED"`.** `PENDING` means wait for `PAYMENT.CAPTURE.COMPLETED`.
- Capture can also return `DECLINED` with HTTP 201. Check the status, not only the HTTP code.
- `INSTRUMENT_DECLINED` / `PAYER_ACTION_REQUIRED` (422) means the buyer must pick another funding source. With the v5 Buttons, `return actions.restart()`. With v6, start the session again.
- `ORDER_ALREADY_CAPTURED` (422) on a retry without the same request id: `GET` the order and read its capture.
- `PREVIOUS_REQUEST_IN_PROGRESS` (409): retry with backoff.
- `ORDER_NOT_APPROVED`, `TRANSACTION_REFUSED`, `PAYEE_ACCOUNT_RESTRICTED`, `MAX_NUMBER_OF_PAYMENT_ATTEMPTS_EXCEEDED` and `DUPLICATE_INVOICE_ID` are the other common ones.

```ts
// src/lib/paypal/orders.ts
import { pp } from "./client";

export async function createEscrowOrder(e: { id: string; title: string; amount: string; currency?: string; attempt?: number }) {
  const currency = e.currency ?? "USD";
  return pp<{ id: string; status: string; links: { rel: string; href: string }[] }>("/v2/checkout/orders", {
    requestId: `create-${e.id}-${e.attempt ?? 1}`,
    prefer: "return=representation",
    body: {
      intent: "CAPTURE",
      purchase_units: [{
        reference_id: e.id, custom_id: e.id, invoice_id: `KEPT-${e.id}-${e.attempt ?? 1}`,
        description: e.title.slice(0, 127),
        amount: { currency_code: currency, value: e.amount,
                  breakdown: { item_total: { currency_code: currency, value: e.amount } } },
        items: [{ name: e.title.slice(0, 127), quantity: "1", category: "DIGITAL_GOODS",
                  unit_amount: { currency_code: currency, value: e.amount } }],
      }],
      payment_source: { paypal: { experience_context: {
        brand_name: "Kept", user_action: "PAY_NOW", shipping_preference: "NO_SHIPPING",
        payment_method_preference: "IMMEDIATE_PAYMENT_REQUIRED",
        return_url: `${process.env.APP_URL}/escrow/${e.id}/paypal/return`,
        cancel_url: `${process.env.APP_URL}/escrow/${e.id}/paypal/cancel`,
      } } },
    },
  });
}

export async function captureOrder(orderId: string) {
  const order = await pp<any>(`/v2/checkout/orders/${orderId}/capture`, {
    body: {}, requestId: `capture-${orderId}`, prefer: "return=representation",
  });
  const cap = order.purchase_units?.[0]?.payments?.captures?.[0];
  return {
    orderStatus: order.status as string,
    captureId: cap?.id as string,
    captureStatus: cap?.status as string,
    gross: cap?.seller_receivable_breakdown?.gross_amount?.value as string,
    paypalFee: cap?.seller_receivable_breakdown?.paypal_fee?.value as string | undefined,
    net: cap?.seller_receivable_breakdown?.net_amount?.value as string | undefined,
    customId: cap?.custom_id as string,
    payerId: order.payer?.payer_id as string,
    payerEmail: order.payer?.email_address as string,
    raw: order,
  };
}
```

> **Server-side amount authority:** never accept the amount from the browser. `createOrder` on the client should POST only the escrow id, and the server looks up the amount. On capture, check that `cap.custom_id === escrowId` and that the amount matches your DB.

## 3. Payments v2: refunds

- `POST /v2/payments/captures/{capture_id}/refund` [spec]
- Headers: `PayPal-Request-Id` (the docs say refund idempotency keys are kept for **45 days**) and `Prefer: return=representation`.
- Body (all optional; **an empty body means a full refund**):

```json
{ "amount": { "currency_code": "USD", "value": "40.00" },
  "note_to_payer": "Partial refund: milestone 2 cancelled",   // <=255, shown to payer
  "invoice_id": "KEPT-escrow_8f2c-R1",                       // <=127
  "custom_id": "escrow_8f2c" }                               // <=127
```

- Response: `{ id, status, status_details?, amount, note_to_payer, seller_payable_breakdown: { gross_amount, paypal_fee, net_amount, total_refunded_amount, ... }, links }`.
- Refund `status`: `COMPLETED | PENDING | FAILED | CANCELLED`. `status_details.reason` is `ECHECK` when pending.
- After a refund, the capture status becomes `PARTIALLY_REFUNDED` or `REFUNDED`. You can issue several partial refunds until the captured amount is exhausted.
- Other endpoints: `GET /v2/payments/refunds/{refund_id}` and `GET /v2/payments/captures/{capture_id}`.
- Errors: `REFUND_AMOUNT_EXCEEDED` (422), `TRANSACTION_DISPUTED` (422), `PREVIOUS_REQUEST_IN_PROGRESS` (409) [spec]. Also documented: `CAPTURE_FULLY_REFUNDED`, `REFUND_TIME_LIMIT_EXCEEDED` (refunds are allowed for about 180 days), `REFUND_NOT_ALLOWED`, `PENDING_CAPTURE`, `REFUND_FAILED_INSUFFICIENT_FUNDS`, `MAX_NUMBER_OF_REFUNDS_EXCEEDED`, `PARTIAL_REFUND_NOT_ALLOWED`. Treat all of these as "issue" strings in `details[0].issue`.
- **Fees [inferred]:** on US accounts PayPal does not return the fixed part of the fee on refunds. A refund is debited from the platform's balance, so if you already paid out part of the escrow, a later refund can push the balance negative. Track `held = captured - refunded - paidOut` in your own ledger and refuse operations that exceed it.

```ts
export async function refundCapture(captureId: string, opts: { escrowId: string; amount?: string; currency?: string; note?: string; seq: number }) {
  return pp<any>(`/v2/payments/captures/${captureId}/refund`, {
    requestId: `refund-${opts.escrowId}-${opts.seq}`,       // deterministic => double-click safe
    prefer: "return=representation",
    body: {
      ...(opts.amount ? { amount: { currency_code: opts.currency ?? "USD", value: opts.amount } } : {}),
      ...(opts.note ? { note_to_payer: opts.note.slice(0, 255) } : {}),
      custom_id: opts.escrowId,
      invoice_id: `KEPT-${opts.escrowId}-R${opts.seq}`,
    },
  });
}
```

## 4. Payouts v1: releasing funds to the freelancer

### Endpoints [spec]
| Op | Endpoint |
|---|---|
| Create batch | `POST /v1/payments/payouts` (header `PayPal-Request-Id`, keys stored 30 days) |
| Batch status | `GET /v1/payments/payouts/{payout_batch_id}?page=1&page_size=1000&total_required=true&fields=...` |
| Item status | `GET /v1/payments/payouts-item/{payout_item_id}` |
| Cancel unclaimed item | `POST /v1/payments/payouts-item/{payout_item_id}/cancel` (only when UNCLAIMED; result status is `RETURNED`) |

### Request
```jsonc
POST /v1/payments/payouts
PayPal-Request-Id: release-escrow_8f2c
{
  "sender_batch_header": {
    "sender_batch_id": "release-escrow_8f2c",   // dedupe: reused within 30 days => rejected, links to original batch
    "email_subject": "You've been paid for 'Landing page' on Kept",
    "email_message": "Your client approved the milestone.",
    "recipient_type": "EMAIL"                    // optional default for items
  },
  "items": [{
    "recipient_type": "EMAIL",                   // EMAIL | PHONE (not in sandbox) | PAYPAL_ID (payer_id; from Log in with PayPal)
    "receiver": "sb-abc123@personal.example.com",// <=127
    "amount": { "value": "95.00", "currency": "USD" },   // NOTE: "currency", NOT "currency_code"
    "note": "Milestone 1 - escrow_8f2c",         // <=4000 ASCII; batch+item notes concatenated <=1000
    "sender_item_id": "escrow_8f2c-m1",          // <=63, your id (echoed in item + webhooks)
    "recipient_wallet": "PAYPAL",                // PAYPAL | VENMO (Venmo needs US phone + note)
    "purpose": "SERVICES"                        // AWARDS|PRIZES|DONATIONS|GOODS|SERVICES|REBATES|CASHBACK|DISCOUNTS|NON_GOODS_OR_SERVICES
  }]
}
```
Response `201`:
```json
{ "batch_header": { "payout_batch_id": "5UXD2E8A7EBQJ", "batch_status": "PENDING",
    "sender_batch_header": { "sender_batch_id": "release-escrow_8f2c", "email_subject": "..." } },
  "links": [{ "href": ".../v1/payments/payouts/5UXD2E8A7EBQJ", "rel": "self", "method": "GET" }] }
```

GET batch returns `batch_header` with `batch_status`, `time_created`, `time_completed`, `amount`, `fees` and `funding_source`, plus `items[]` with `payout_item_id`, `transaction_id`, `transaction_status`, `payout_item_fee`, `payout_item {amount, receiver, sender_item_id, note, recipient_wallet}`, `time_processed` and `errors`.

### Statuses [spec]
- `batch_status`: `DENIED | PENDING | PROCESSING | SUCCESS | CANCELED`.
  **A `SUCCESS` batch means the batch finished processing. It does not mean every item was paid.** Always read each item's status.
- Item `transaction_status`:
  - `SUCCESS`: funds credited.
  - `PENDING`: still processing.
  - `UNCLAIMED`: the receiver has no PayPal account, or has an unconfirmed email. They get **30 days** to claim, after which the item becomes `RETURNED` and the money comes back.
  - `FAILED`, `RETURNED`, `ONHOLD` (risk review), `BLOCKED`, `REFUNDED`, `REVERSED`.
- Map item statuses into the escrow ledger as follows:
  - `SUCCESS` means released.
  - `PENDING`, `ONHOLD` and `UNCLAIMED` mean release in flight; show "awaiting freelancer claim" for `UNCLAIMED`.
  - `FAILED`, `RETURNED`, `BLOCKED` and `REVERSED` mean the funds are back in held, so alert and allow a retry with a **new** `sender_batch_id` (for example `release-<id>-2`).

### Sandbox specifics
- The platform sender is your sandbox **business** account (the one the REST app is linked to). It needs **a PayPal balance**. Captures from sandbox buyers normally land in the balance right away [inferred]. Payout amount plus fees above the balance gives `INSUFFICIENT_FUNDS`.
- **Payouts permission:** in Developer Dashboard > Apps & Credentials > your sandbox app > Features, make sure **Payouts** is checked. It is on by default for sandbox apps [inferred]. A missing permission shows up as 403 `AUTHORIZATION_ERROR` / `NOT_AUTHORIZED` / "Authorization error occurred". After toggling it, mint a new token.
  **Live Payouts must be requested and approved** on the live business account.
- **Receivers:** use the email of a **sandbox personal account** (Dashboard > Testing Tools > Sandbox Accounts, for example `sb-xxxx@personal.example.com`). That gives `SUCCESS`. Sending to an email that has no sandbox account gives an **`UNCLAIMED`** item, which is a handy way to test that path. You cannot pay the sender's own account.
- `PHONE` is **not supported** in sandbox [spec].
- Sandbox emails are not delivered. Log in to `https://www.sandbox.paypal.com` as the receiver to see the payment.
- **Negative testing (test values)** for payouts: put the code in `items[0].note`, or in `sender_batch_header.sender_batch_id` for 013, or use a path like `GET /v1/payments/payouts/ERRPYO015`. Codes are case-sensitive.

| `ERRPYO002` | `SENDER_EMAIL_UNCONFIRMED` |

Webhooks are tied to the **REST app** (client id). [inferred] Each app has a small webhook limit (about 10), and creating a duplicate URL fails with `WEBHOOK_URL_ALREADY_EXISTS`.

### Delivery semantics [docs]
Return a 2xx quickly. PayPal retries **up to 25 times over 3 days**. Delivery is at-least-once and can arrive out of order, so make handlers idempotent: store `event.id`, and compare resource status before moving state.

### Verification option A: postback [spec]
`POST /v1/notifications/verify-webhook-signature`. All fields below are required:

```json
{ "auth_algo": "<PAYPAL-AUTH-ALGO header>",
  "cert_url": "<PAYPAL-CERT-URL header>",
  "transmission_id": "<PAYPAL-TRANSMISSION-ID header>",
  "transmission_sig": "<PAYPAL-TRANSMISSION-SIG header>",
  "transmission_time": "<PAYPAL-TRANSMISSION-TIME header>",
  "webhook_id": "<your webhook id>",
  "webhook_event": { ...the event exactly as received... } }
```

The response is `{ "verification_status": "SUCCESS" | "FAILURE" }`.

**Gotcha:** "webhook_event data [must] be posted back exactly as it was received… re-serializing … can fail verification". Splice the **raw** body string into the JSON instead of `JSON.stringify(parsed)`.

### Verification option B: self-verify (preferred by PayPal, no extra API call)
Build the message `transmissionId|transmissionTime|webhookId|crc32(rawBody)`, with the CRC32 as an unsigned decimal. Then verify the base64 `paypal-transmission-sig` with RSA-SHA256 against the cert at `paypal-cert-url`. Cache the cert, and **check that the cert host ends in `.paypal.com`** to prevent forged-cert attacks.

```ts
// src/app/api/paypal/webhook/route.ts
import { crc32 } from "node:zlib";      // Node >= 20.15 / 22.2 (repo runs Node 22)
import crypto from "node:crypto";
import { PAYPAL_API, getAccessToken } from "@/lib/paypal/client";

export const runtime = "nodejs";
export const dynamic = "force-dynamic";

const certCache = new Map<string, string>();

async function selfVerify(raw: string, h: Headers, webhookId: string): Promise<boolean> {
  const tid = h.get("paypal-transmission-id"), ts = h.get("paypal-transmission-time");
  const sig = h.get("paypal-transmission-sig"), certUrl = h.get("paypal-cert-url");
  if (!tid || !ts || !sig || !certUrl) return false;
  const u = new URL(certUrl);
  if (u.protocol !== "https:" || !(u.hostname === "paypal.com" || u.hostname.endsWith(".paypal.com"))) return false;
  let pem = certCache.get(certUrl);
  if (!pem) { pem = await (await fetch(certUrl)).text(); certCache.set(certUrl, pem); }
  const message = `${tid}|${ts}|${webhookId}|${crc32(Buffer.from(raw, "utf8"))}`;
  return crypto.createVerify("SHA256").update(message).verify(pem, sig, "base64");
}

async function postbackVerify(raw: string, h: Headers, webhookId: string): Promise<boolean> {
  const meta = {
    auth_algo: h.get("paypal-auth-algo"), cert_url: h.get("paypal-cert-url"),
    transmission_id: h.get("paypal-transmission-id"), transmission_sig: h.get("paypal-transmission-sig"),
    transmission_time: h.get("paypal-transmission-time"), webhook_id: webhookId,
  };
  // splice the RAW body in (pp() would re-stringify a parsed object, which can break verification)
  const body = JSON.stringify(meta).slice(0, -1) + `,"webhook_event":${raw}}`;
  const res = await fetch(`${PAYPAL_API}/v1/notifications/verify-webhook-signature`, {
    method: "POST", cache: "no-store", body,
    headers: { Authorization: `Bearer ${await getAccessToken()}`, "Content-Type": "application/json" },
  });
  if (!res.ok) return false;
  return ((await res.json()) as { verification_status: string }).verification_status === "SUCCESS";
}

export async function POST(req: Request) {
  const raw = await req.text();                         // RAW body — do not use req.json() first
  const ok = await selfVerify(raw, req.headers, process.env.PAYPAL_WEBHOOK_ID!);
  if (!ok) return new Response("bad signature", { status: 400 });
  const event = JSON.parse(raw) as { id: string; event_type: string; resource: any; resource_type: string };
  // idempotency: insert event.id into paypal_events (unique) — if exists, return 200
  switch (event.event_type) {
    case "PAYMENT.CAPTURE.COMPLETED":   /* escrow = event.resource.custom_id; mark HELD with capture id */ break;
    case "PAYMENT.CAPTURE.REFUNDED":    /* event.resource is a refund; capture id in links rel=up */ break;
    case "PAYMENT.PAYOUTS-ITEM.SUCCEEDED":
    case "PAYMENT.PAYOUTS-ITEM.UNCLAIMED":
    case "PAYMENT.PAYOUTS-ITEM.FAILED":
    case "PAYMENT.PAYOUTS-ITEM.RETURNED": /* event.resource.payout_item.sender_item_id = escrowId; transaction_status */ break;
  }
  return new Response("ok");
}
```

### Simulator [docs]

## 6. JS SDK: v6 (recommended) vs classic v5

### Status
- **JS SDK v6** ("Web SDK v6") is generally available. PayPal says it has "full feature parity" and calls v5 "deprecated" in the v5 to v6 upgrade guide. No v5 end-of-life date was found.
- `@paypal/react-paypal-js` **v9 and later** made v6 the primary API; **10.5.2** is current. The root import still exports the legacy v5 components (`PayPalScriptProvider`, `PayPalButtons`). The v6 API lives at `@paypal/react-paypal-js/sdk-v6`.

| | v5 (classic) | v6 |
|---|---|---|
| Script | `https://www.paypal.com/sdk/js?client-id=...&currency=USD&intent=capture&components=buttons` | `https://www.{sandbox.}paypal.com/web-sdk/v6/core` |
| Environment | Implied by the client-id | **Explicit `environment: "sandbox" \| "production"`** (a live client id still loads sandbox if you say sandbox) |
| Init | Global `paypal.Buttons({...}).render("#el")` | `paypal.createInstance({ clientId \| clientToken, components: ["paypal-payments"], pageType })` |
| Buttons | iframe buttons | `<paypal-button>` web components, plus a session you `start()` |
| Eligibility | Implicit | Explicit `findEligibleMethods` / `useEligibleMethods` (can be pre-fetched server-side through `POST /v2/payments/find-eligible-methods`) |
| `createOrder` returns | `orderID` string | `{ orderId }` |
| `onApprove` data | `{ orderID, payerID }` | `{ orderId, payerId?, fundingSource }` |
| Currency and intent | URL query params | Defined only by the server-side order |

### Recommended: v6 with React in the Next.js App Router
```tsx
// src/components/paypal/EscrowPayButton.tsx
"use client";
import { PayPalProvider, PayPalOneTimePaymentButton, usePayPal, INSTANCE_LOADING_STATE } from "@paypal/react-paypal-js/sdk-v6";

export function EscrowPay({ escrowId, onPaid }: { escrowId: string; onPaid: () => void }) {
  return (
    <PayPalProvider clientId={process.env.NEXT_PUBLIC_PAYPAL_CLIENT_ID!} environment="sandbox"
                    components={["paypal-payments"]} pageType="checkout">
      <Inner escrowId={escrowId} onPaid={onPaid} />
    </PayPalProvider>
  );
}

function Inner({ escrowId, onPaid }: { escrowId: string; onPaid: () => void }) {
  const { loadingStatus, error } = usePayPal();
  if (loadingStatus === INSTANCE_LOADING_STATE.PENDING) return <div>Loading PayPal…</div>;
  if (loadingStatus === INSTANCE_LOADING_STATE.REJECTED) return <div>PayPal failed: {error?.message}</div>;
  return (
    <PayPalOneTimePaymentButton
      presentationMode="auto"            // "auto" | "popup" | "modal" | "redirect"
      createOrder={async () => {
        const r = await fetch(`/api/escrows/${escrowId}/paypal/order`, { method: "POST" });
        if (!r.ok) throw new Error("create order failed");
        const { id } = await r.json();
        return { orderId: id };
      }}
      onApprove={async ({ orderId }) => {          // MUST return/await the capture promise
        const r = await fetch(`/api/escrows/${escrowId}/paypal/capture`, {
          method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.stringify({ orderId }) });
        if (!r.ok) throw new Error(`capture failed ${r.status}`);
        onPaid();
      }}
      onCancel={() => {}}
      onError={(e) => console.error(e)}
    />
  );
}
```

- Route handlers `app/api/escrows/[id]/paypal/order/route.ts` and `.../capture/route.ts` call `createEscrowOrder` and `captureOrder` from section 2.
- **COOP header:** popup flows need `Cross-Origin-Opener-Policy: same-origin-allow-popups` (or no COOP) on the checkout page. PayPal's v6 sample sets it explicitly. If you add security headers in `next.config.ts`, do not set `same-origin`.
- **SSR:** `PayPalProvider` handles hydration. You can pre-fetch eligibility in a Server Component with `fetchEligibleMethods` from `@paypal/react-paypal-js/sdk-v6/server` and pass `eligibleMethodsResponse` as a resolved value, not a promise. This is optional.
- For the redirect presentation mode, the `return_url`/`cancel_url` pages must call capture themselves. The approved order id is in the `token` query parameter.

### Fallback: classic v5 (same package, root import)
```tsx
"use client";
import { PayPalScriptProvider, PayPalButtons } from "@paypal/react-paypal-js";
<PayPalScriptProvider options={{ clientId: process.env.NEXT_PUBLIC_PAYPAL_CLIENT_ID!, currency: "USD", intent: "capture" }}>

```

## 7. Log in with PayPal (OIDC) in sandbox

**Dashboard setup:** Apps & Credentials (Sandbox) > your app.
1. Under Features / Other features, tick **Log in with PayPal**, then open **Advanced Settings**.
2. Add a **Return URL**, for example `http://localhost:3000/api/auth/paypal/callback`. [inferred] Sandbox accepts localhost; live requires HTTPS and an exact match.
3. Pick the **information requested**: Email, full name, and **Account verification status** plus **PayPal account ID (payer ID)**. The last two map to the `paypalattributes` scope.
4. Enter a **Privacy policy URL** and **User agreement URL** (example.com is fine in sandbox).
5. Save. Live apps are **reviewed** by PayPal, which can take a while; sandbox needs no review.
6. Log in with a **sandbox personal account**.

```ts
import {
  Client, Environment, LogLevel, ApiError,
  OrdersController, PaymentsController,
  CheckoutPaymentIntent, PaypalExperienceUserAction, PaypalWalletContextShippingPreference, ItemCategory,
} from "@paypal/paypal-server-sdk";

const client = new Client({
  clientCredentialsAuthCredentials: { oAuthClientId: process.env.PAYPAL_CLIENT_ID!, oAuthClientSecret: process.env.PAYPAL_CLIENT_SECRET! },
  environment: process.env.PAYPAL_ENV === "live" ? Environment.Production : Environment.Sandbox,
  timeout: 0,
  logging: { logLevel: LogLevel.Warn, logRequest: { logBody: false }, logResponse: { logHeaders: false } },
});
const orders = new OrdersController(client);
const payments = new PaymentsController(client);

export async function sdkCreateOrder(escrowId: string, amount: string) {
  const { result } = await orders.createOrder({
    paypalRequestId: `create-${escrowId}`,
    prefer: "return=representation",
    body: {
      intent: CheckoutPaymentIntent.Capture,
      purchaseUnits: [{
        referenceId: escrowId, customId: escrowId, invoiceId: `KEPT-${escrowId}`, description: "Escrow deposit",
        amount: { currencyCode: "USD", value: amount, breakdown: { itemTotal: { currencyCode: "USD", value: amount } } },
        items: [{ name: "Escrow deposit", quantity: "1", category: ItemCategory.DigitalGoods,
                  unitAmount: { currencyCode: "USD", value: amount } }],
      }],
      paymentSource: { paypal: { experienceContext: {
        brandName: "Kept", userAction: PaypalExperienceUserAction.PayNow,
        shippingPreference: PaypalWalletContextShippingPreference.NoShipping,
        returnUrl: `${process.env.APP_URL}/paypal/return`, cancelUrl: `${process.env.APP_URL}/paypal/cancel`,
      } } },
    },
  });
  return result; // result.id, result.status, result.links
}

export async function sdkCapture(orderId: string) {
  try {
    const { result } = await orders.captureOrder({ id: orderId, paypalRequestId: `capture-${orderId}`, prefer: "return=representation" });
    const cap = result.purchaseUnits?.[0]?.payments?.captures?.[0];
    return { captureId: cap?.id, status: cap?.status, fee: cap?.sellerReceivableBreakdown?.paypalFee?.value,
             net: cap?.sellerReceivableBreakdown?.netAmount?.value, customId: cap?.customId };
  } catch (e) {
    if (e instanceof ApiError) {
      // e.statusCode, e.result (parsed error: { name, details: [{ issue }], debug_id }), e.body (raw)
      const issue = (e.result as any)?.details?.[0]?.issue;
      throw Object.assign(new Error(`capture failed: ${issue ?? e.statusCode}`), { issue, statusCode: e.statusCode });
    }
    throw e;
  }
}

export async function sdkRefund(captureId: string, escrowId: string, seq: number, amount?: string) {
  const { result } = await payments.refundCapturedPayment({
    captureId, paypalRequestId: `refund-${escrowId}-${seq}`, prefer: "return=representation",
    body: { ...(amount ? { amount: { currencyCode: "USD", value: amount } } : {}), noteToPayer: "Escrow partial refund",
            customId: escrowId, invoiceId: `KEPT-${escrowId}-R${seq}` },
  });
  return result; // result.id, result.status ("COMPLETED" | "PENDING" | ...)
}
```

**Verdict:** using the SDK for Orders and Payments is fine and gives typed enums. Plain fetch is simpler, consistent with Payouts and Webhooks, and avoids the BigInt and camelCase mapping surprises. Pick one style per module.

- **Compatibility gotcha:** the `ai-sdk` export imports `Tool, LanguageModelV1` from `ai` and declares `ai@^4`. Tools use the v4 `parameters` shape. Today's `ai` is **7.0.x** (dist-tags also carry `ai-v5` and `ai-v6`). With AI SDK 5+ you would need adapters, or pin `ai@4` just for this. The package also pulls in `openai@4.86.1`, `@langchain/core@0.3.6` and `@paypal/paypal-server-sdk@^1` (an old major, separate from our 2.5).
- **This repo uses `@anthropic-ai/sdk` and `@modelcontextprotocol/sdk`, not `ai`.** The cleanest options are:
  1. **Remote MCP** at `https://mcp.sandbox.paypal.com/http` (Streamable HTTP) or `/sse`. For production use `https://mcp.paypal.com/http`. Auth is either an OAuth login and consent flow (in MCP hosts through `npx mcp-remote <url>`) or a header `Authorization: Bearer <PayPal access token>`. You can connect with `@modelcontextprotocol/sdk`'s `StreamableHTTPClientTransport` (passing `requestInit.headers`), or pass it to the Anthropic Messages API MCP connector as a URL plus `authorization_token`. **[inferred]** Test that the bearer access-token path works in sandbox before relying on it.
  2. **In-process:** `import { PayPalAgentToolkit } from "@paypal/agent-toolkit/mcp"` is an `McpServer` subclass (`new PayPalAgentToolkit({ accessToken, configuration })`). Connect it to an MCP client with an in-memory transport and expose its tools to Claude.
  3. **Local stdio:** `npx -y @paypal/mcp --tools=all` with `PAYPAL_ACCESS_TOKEN` and `PAYPAL_ENVIRONMENT=SANDBOX`.
- **Worth integrating?** Not for the escrow money path. Keep create, capture, refund and payout as deterministic server code with idempotency keys; never let an LLM move money directly. It is reasonable as a **read-mostly assistant** feature: "summarise open disputes", "draft an invoice for milestone 2", "list my transactions this week". Gate any write tool (refund, accept_dispute_claim) behind explicit human confirmation in the UI. For a hackathon demo, the remote MCP server is the cheapest integration and shows the "AI plus PayPal" story.

## 11. Production path for "hold then release" (compliance)

**What the hackathon flow is legally:** money moves client → platform PayPal balance → (later) Payouts → freelancer. The platform **takes custody of third-party funds** and decides who gets them. That is an escrow or money-transmission activity.
- US: state money transmitter licences and FinCEN MSB status; EU/UK: e-money or payment institution rules.
- PayPal's **Acceptable Use Policy** (last updated 2022-10-29) lists under *Activities Requiring Approval*, item 4, Payment Facilitator: "Providing payment services which would fall under the definition of a money service business or an electronic money institution. **Services would also include the sale of stored value cards and escrow services.**"
- So running this live on a normal business account without PayPal pre-approval risks account limitation and fund holds.
- **Fine for a sandbox demo. Do not ship it as-is.**

**How a real startup does it on PayPal** (the platform never touches the money):
1. **Join the PayPal partner program**, now called PayPal Complete Payments (PPCP) / "Multiparty" (formerly PayPal Commerce Platform). Platform approval comes through PayPal sales and partner onboarding. You get a partner client id and a **BN code** (`PayPal-Partner-Attribution-Id`).
2. **Onboard each freelancer as a seller** with Partner Referrals v2 (`POST /v2/customer/partner-referrals`):
   ```json
   { "tracking_id": "freelancer_123",
     "operations": [{ "operation": "API_INTEGRATION",
       "api_integration_preference": { "rest_api_integration": {
         "integration_method": "PAYPAL", "integration_type": "THIRD_PARTY",
         "third_party_details": { "features": ["PAYMENT", "REFUND", "PARTNER_FEE", "DELAY_FUNDS_DISBURSEMENT", "READ_SELLER_DISPUTE", "UPDATE_SELLER_DISPUTE"] } } } }],
     "products": ["PPCP"],
     "legal_consents": [{ "type": "SHARE_DATA_CONSENT", "granted": true }],
     "partner_config_override": { "return_url": "https://app.example.com/onboarding/paypal/return" } }
   ```
   - Redirect the freelancer to the `action_url` link.
   - On return, or on the `MERCHANT.ONBOARDING.COMPLETED` webhook, resolve the merchant id with `GET /v1/customer/partners/{partner_merchant_id}/merchant-integrations?tracking_id=freelancer_123`.
   - Check `GET .../merchant-integrations/{merchant_id}` for `payments_receivable: true`, `primary_email_confirmed: true` and the granted OAuth integrations.
   - Spec enum notes: features include `DELAY_FUNDS_DISBURSEMENT`, `PARTNER_FEE`, `PAYOUTS`; products include `PPCP`, `EXPRESS_CHECKOUT`, `PAYPAL_COMMERCE_PLATFORM_BUSINESS`.
3. **Create the order with the freelancer as payee and delayed disbursement.** Headers: `PayPal-Partner-Attribution-Id: <BN>` and optionally `PayPal-Auth-Assertion`.
   ```json
   "purchase_units": [{ "amount": {...}, "custom_id": "escrow_8f2c",
     "payee": { "merchant_id": "<freelancer merchant id>" },
     "payment_instruction": { "disbursement_mode": "DELAYED",
       "platform_fees": [{ "amount": { "currency_code": "USD", "value": "10.00" } }] } }]
   ```
   On capture, the money settles in the **freelancer's** PayPal account but is **held by PayPal** (`disbursement_mode: DELAYED` appears on the capture). The PayPal fee is deducted from the seller; the platform fee goes to the partner.
4. **Release:** `POST /v1/payments/referenced-payouts-items` with `{ "reference_id": "<capture id>", "reference_type": "TRANSACTION_ID" }` and headers `PayPal-Partner-Attribution-Id` and `PayPal-Request-Id`.
   - Response: `{ item_id, processing_state: { status: "SUCCESS" | "PROCESSING" | ... }, reference_id, reference_type, payout_amount, payout_destination }`.
   - Webhooks: `PAYMENT.REFERENCED-PAYOUT-ITEM.COMPLETED` / `.FAILED`.
   - **If you never call release, PayPal auto-disburses after 28 days.** Hold periods longer than 28 days cannot be modelled this way. Long milestones need separate orders per milestone, or authorize-then-capture.
5. **Refund while held:** refund the capture as usual (`/v2/payments/captures/{id}/refund`, sent on behalf of the seller with `PayPal-Auth-Assertion`). Refund the platform fee too if needed (`payment_instruction.platform_fees` in the refund body).
6. **Disputes and chargebacks** belong to the seller (the merchant of record). The platform reads and updates them with the `READ_SELLER_DISPUTE` / `UPDATE_SELLER_DISPUTE` features.
7. Alternative for short holds without multiparty: `intent: AUTHORIZE`, then `POST /v2/payments/authorizations/{id}/capture` later. The authorization is valid for 29 days with a 3-day honour period [inferred]. The buyer keeps the money until capture. Payout to the freelancer still needs a compliant rail, so this alone does not solve custody.
8. For pure **payouts at scale or KYC'd payees**, PayPal's Hyperwallet (partner-referral product `HYPERWALLET_PAYOUTS`) is the regulated payout rail, and needs a contract.

**Summary:** in production the platform is a **marketplace facilitator**. PayPal is the regulated holder; you only instruct "hold" (`DELAYED`) and "release" (`referenced-payouts-items`) and collect `platform_fees`. That is how you avoid becoming a money transmitter. It requires PayPal partner approval, so plan for weeks. Talk to counsel and PayPal partner sales.

## 12. Disputes API v1 (`/v1/customer/disputes`) [spec]

| Op | Endpoint |
|---|---|
| List | `GET /v1/customer/disputes?start_time=&disputed_transaction_id=&dispute_state=&page_size=&next_page_token=&update_time_before=&update_time_after=` |
| Get | `GET /v1/customer/disputes/{id}` |
| Provide evidence | `POST .../{id}/provide-evidence` (multipart: `input` JSON plus `evidence-file`) |
| Accept claim (refunds buyer) | `POST .../{id}/accept-claim` with `accept_claim_type`, `note`, `refund_amount` |
| Make offer (INQUIRY stage only) | `POST .../{id}/make-offer` with `{ note, offer_type: REFUND \| REFUND_WITH_RETURN \| REFUND_WITH_REPLACEMENT \| REPLACEMENT_WITHOUT_REFUND, offer_amount }` |
| Escalate to claim | `POST .../{id}/escalate` |
| Send message | `POST .../{id}/send-message` |
| Appeal | `POST .../{id}/appeal` |
| Other | `PATCH .../{id}`, `accept-offer`, `deny-offer`, `acknowledge-return-item`, `provide-supporting-info` |
| **Sandbox only** | `POST .../{id}/require-evidence` (moves UNDER_REVIEW to WAITING_FOR_BUYER_RESPONSE or WAITING_FOR_SELLER_RESPONSE) and `POST .../{id}/adjudicate` with `{ "adjudication_outcome": "BUYER_FAVOR" \| "SELLER_FAVOR" }` (requires UNDER_REVIEW) |

Filter and field notes:
- `start_time` must be within the last 180 days. Use either `start_time` or `disputed_transaction_id`, not both.
- `accept_claim_type` values: `REFUND`, `REFUND_WITH_RETURN`, `PARTIAL_REFUND`, `REFUND_WITH_RETURN_SHIPMENT_LABEL`.
- A dispute's `disputed_transactions[].seller_transaction_id` is the capture id. Match it to the escrow and **freeze release while the dispute is open**.

Enums:
- `status`: `OPEN | WAITING_FOR_BUYER_RESPONSE | WAITING_FOR_SELLER_RESPONSE | UNDER_REVIEW | RESOLVED | OTHER`
- `dispute_state` filter: `OPEN_INQUIRIES | REQUIRED_ACTION | REQUIRED_OTHER_PARTY_ACTION | UNDER_PAYPAL_REVIEW | APPEALABLE | RESOLVED`
- `dispute_life_cycle_stage`: `INQUIRY | CHARGEBACK | PRE_ARBITRATION | ARBITRATION`
- `reason`: `MERCHANDISE_OR_SERVICE_NOT_RECEIVED | MERCHANDISE_OR_SERVICE_NOT_AS_DESCRIBED | UNAUTHORISED | CREDIT_NOT_PROCESSED | DUPLICATE_TRANSACTION | INCORRECT_AMOUNT | PAYMENT_BY_OTHER_MEANS | CANCELED_RECURRING_BILLING | PROBLEM_WITH_REMITTANCE | OTHER`

Webhooks: `CUSTOMER.DISPUTE.CREATED`, `.UPDATED`, `.RESOLVED`. The app needs the Disputes feature enabled. On Payouts-based escrow, a dispute on a capture you already paid out means the **platform** is liable, which is another reason to use multiparty in production.

## 13. Gotchas checklist

1. **`currency` vs `currency_code`:** Payouts v1 uses `amount.currency`. Orders, Payments and Referenced Payouts use `currency_code`.
2. **Idempotency:**
   - Orders: `PayPal-Request-Id`, 6 h.
   - Refunds: `PayPal-Request-Id`, 45 d.
   - Payouts: `sender_batch_id`, 30 d (plus `PayPal-Request-Id`).
   - Derive all of them deterministically from escrow ids so double-clicks and retries are safe.
3. **`invoice_id` must be unique per merchant**, so reusing it gives `DUPLICATE_INVOICE_ID`. Include an attempt counter, or omit it.
4. **Use `custom_id` to correlate.** It is echoed on captures and capture webhooks and is invisible to the payer. Payout items use `sender_item_id`.
5. **Capture `status`, not HTTP status, decides "held".** Only `COMPLETED` counts. Set `payment_method_preference: IMMEDIATE_PAYMENT_REQUIRED` to avoid eCheck `PENDING`.
6. **A batch `SUCCESS` is not an item `SUCCESS`.** `UNCLAIMED` returns after 30 days.
7. **Webhooks:**
   - Verify using the raw body.
   - Simulator events cannot be postback-verified; their id is `WEBHOOK_ID`.
   - Delivery is at-least-once with 25 retries over 3 days. Dedupe on `event.id`.
   - The listener must be public HTTPS.
8. **`PAYMENT.CAPTURE.REFUNDED`'s resource is the refund**, not the capture. Follow the `rel: "up"` link to the capture.
9. **Re-mint tokens after changing app features or scopes.** Cache tokens otherwise.
10. **v6 needs an explicit `environment`**, because the client id does not select it. `onApprove` must return the capture promise. Popups need COOP `same-origin-allow-popups`.
11. **Do not trust client amounts.** Look up the escrow server-side, and assert `custom_id` and amount after capture.
12. **Platform balance accounting:** PayPal fees reduce net (`seller_receivable_breakdown.paypal_fee`). Payouts carry their own fee (`payout_item_fee`). Refunds after payout can overdraw. Keep a ledger of `held = captured_net - refunded - paid_out - payout_fees`.
13. **Log `paypal-debug-id`** (response header) and `debug_id` on every error.
14. **Negative-testing headers and ERRPYO values are sandbox-only.** Strip them in live.
15. **Live go-live checklist:**
    - Use separate live app credentials.
    - Request Payouts approval and Log in with PayPal review.
    - Get AUP pre-approval for escrow, or migrate to Multiparty delayed disbursement.
